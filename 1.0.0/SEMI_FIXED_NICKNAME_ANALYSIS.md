# 반고닉(반고정닉) 식별 분석

DCInside에서 `ㅇㅇ`처럼 **여러 사람이 같은 닉네임 텍스트를 공유하는** 상황을, 어떤 신호로
개인 단위까지 갈라낼 수 있는지 정리한 문서다. 목적은 "작성글·댓글 검색"과 "이용자메모"를
닉네임이 아니라 **사람 단위**로 걸 수 있는지를 판정하는 것이다.

모든 관측은 저장소에 캡처된 실제 DOM 픽스처
(`tests/fixtures/dc.html` — programming 갤러리 목록, 작성자 셀 50건)를 근거로 한다.

---

## 1. 결론 요약

| 대상 | 개인 단위 구분 | 근거 신호 | 신뢰도 |
|---|---|---|---|
| 반고닉 ↔ 반고닉 | **가능 (완전)** | `data-uid` (실제 계정 ID) | 높음 |
| 고닉 ↔ 반고닉 | **가능** | 닉 아이콘 `fix_nik.gif` vs `nik.gif` | 높음(단일 픽스처 관측) |
| 유동닉 ↔ 유동닉 | **불가능(원리적)** | 2옥텟 IP뿐 | — |

핵심은 **반고닉은 익명이 아니다**는 점이다. 닉네임 텍스트만 겹칠 뿐,
`data-uid`에 갤로그가 실존하는 고유 계정 ID가 그대로 실려 있다. 따라서 반고닉끼리는
"구분이 불가능한 수준"이 아니라 **이미 완전히 구분 가능**하다. 진짜로 구분이 불가능한
쪽은 반고닉이 아니라 **유동닉**이다.

---

## 2. 세 신분과 DOM 신호 (실측)

작성자 셀은 `<td class="gall_writer ub-writer" data-nick data-uid data-ip>` 형태이고,
내부 `.addbox`의 마크업이 신분에 따라 갈린다.

| 신분 | `data-uid` | `data-ip` | 닉 span | 아이콘 | 픽스처 건수 |
|---|---|---|---|---|---|
| 고닉 (고정닉) | 있음 | 빈 값 | `nickname in` | `fix_nik.gif` | 15 |
| 반고닉 (반고정닉) | **있음** | 빈 값 | `nickname in` | `nik.gif` | 3 |
| 유동닉 | 빈 값 | 2옥텟 | `nickname` | 없음 (`<span class="ip">`) | 32 |

상관관계는 50건 전부에서 **예외 없이** 성립했다 (`fix_nik`+uid 15 / `nik`+uid 3 /
아이콘없음+uid없음 32).

### 2.1 사용자가 관찰한 "노란점 없음"의 정체

> "잘보면 고닉과 달리 회색딱지 옆에 노란점이 없다."

이 관찰은 정확하며, DOM에 **기계 판독 가능한 형태로 남는다**. 두 신분은 서로 다른
이미지 파일을 쓴다.

```html
<!-- 고닉: fix_nik.gif ("fix"ed nickname) -->
<span class='nickname in' title='헤르 미온느'><em>헤르 미온느</em></span>
<a class='writer_nikcon '><img src='.../images/fix_nik.gif'
   title='okoil : 갤로그로 이동합니다.' onClick="window.open('//gallog.dcinside.com/okoil');"></a>

<!-- 반고닉: nik.gif -->
<span class='nickname in' title='ㅇㅇ'><em>ㅇㅇ</em></span>
<a class='writer_nikcon '><img src='.../images/nik.gif'
   title='guest14** : 갤로그로 이동합니다.' onClick="window.open('//gallog.dcinside.com/guest1433');"></a>
```

즉 시각적으로 흐릿한 차이가, 파일명 수준에서는 **이진 신호**다.

### 2.2 갤로그 비공개는 uid를 숨기지 못한다

> "갤로그(활동내역)까지 비공개로 설정하면 사실상 구분이 불가능한 수준"

갤로그 비공개는 **갤로그 페이지의 내용**을 가릴 뿐, 신원 자체는 페이지에 남는다.
위 마크업에서 tooltip은 `guest14**`로 마스킹되지만,

- `data-uid="guest1433"` — 전체 ID
- `onClick`의 갤로그 URL `//gallog.dcinside.com/guest1433` — 전체 ID

두 곳에 **마스킹되지 않은 전체 uid**가 남는다. 사람 눈에는 `guest14**`라 구분이 어렵지만,
확장 프로그램 입장에서는 처음부터 완전한 식별자를 읽고 있다. 사용자가 말한
"아이디를 굳이 체크해야만 구분"이 바로 이 지점이고, 자동화하면 비용이 0이 된다.

## 3. 실측: 닉네임 `ㅇㅇ` 10명

픽스처에서 닉네임이 `ㅇㅇ`인 작성자는 10건이며, 사용자가 우려한 상황이 그대로 재현된다.

| # | data-uid | data-ip | 아이콘 | 판정 |
|---|---|---|---|---|
| 1 | `guest1433` | — | `nik` | 반고닉 A |
| 2 | `chartman` | — | `nik` | 반고닉 B |
| 3 | `table9132` | — | `nik` | 반고닉 C |
| 4 | — | 175.223 | — | 유동닉 |
| 5 | — | 124.48 | — | 유동닉 |
| 6 | — | 223.38 | — | 유동닉 |
| 7 | — | 211.210 | — | 유동닉 |
| 8 | — | 1.213 | — | 유동닉 |
| 9 | — | 117.111 | — | 유동닉 |
| 10 | — | 203.236 | — | 유동닉 |

읽는 법:

- **반고닉 3명(A/B/C)은 서로 완전히 구분된다.** uid가 계정 ID이므로 충돌하지 않는다.
- **유동닉 7건은 서로 구분되지 않는다.** 남은 정보가 2옥텟 IP뿐이다.

대조군으로, 고닉은 닉네임↔uid가 1:1로 안정적이었다
(`헤르 미온느`↔`okoil` 4건, `guiyom.org`↔`concerto7106` 6건). 반고닉만 닉네임이
비어 있는 자리처럼 `ㅇㅇ`로 겹친다.

## 4. 유동닉의 원리적 한계

픽스처의 `data-ip`는 **전부 정확히 2옥텟**이었다 (`175.223`, `1.213`, `43.200` …).
DC가 `/16` 수준까지만 공개하므로 다음 두 방향 모두 깨진다.

- **다른 사람이 같아 보인다**: `175.223`은 이동통신 대역 하나로, 수만~수십만 호스트가
  같은 표기를 공유한다.
- **같은 사람이 달라 보인다**: 모바일은 IP가 수시로 바뀌어, 한 사람이 글마다 다른
  대역으로 찍힌다.

따라서 유동닉 개인 식별은 보강 신호(활동 시간대, 말투, 등장 패턴)로 **추정**만
가능하고 **확정은 불가능**하다. 이 한계는 확장 프로그램이 개선할 수 있는 종류가 아니다.

### 4.1 파생 관찰: `suspiciousIpBands`의 대역 묶기는 사실상 무연산

`src/core/archive/activity-analyzer.js:154`는 대역을 이렇게 만든다.

```js
const band = post.ip.split('.').slice(0, 2).join('.');
```

그런데 입력 `post.ip`가 이미 2옥텟(`175.223`)이므로 `slice(0, 2)`는 값을 바꾸지 않는다.
결과적으로 목록 페이지에서 이 함수의 "IP 대역 묶기"는 **정확한 IP 일치**와 동일하게
동작한다. 같은 이유로 `USER_RULE_TYPES.IP`와 `IP_PREFIX`도 이 데이터에서는 사실상
같은 규칙이 된다. 오동작은 아니지만, "대역으로 넓게 잡는다"는 기대와는 다르다.

또한 `minNicknames = 3` 기준은 위 표의 유동닉 7건처럼 **서로 무관한 사람들이 흔한 닉네임을
공유하는 경우**에도 걸릴 수 있어, 다중이 판정으로 읽으면 오탐이 나온다.

## 5. DC 사이트 자체 메뉴 매핑

작성자 클릭 시 뜨는 7개 항목을 위 신호에 대응시키면 이렇게 갈린다.

| 메뉴 | 식별 단위 | 반고닉 구분력 |
|---|---|---|
| 게시글 / 댓글 / 갤로그 / 작성글검색 | 계정(uid) | **정확** — uid 기반이라 `ㅇㅇ` 3명이 섞이지 않음 |
| 이용자메모 | 계정(uid) | **정확** |
| 차단(닉네임) | 닉네임 텍스트 | **없음** — `ㅇㅇ` 차단 시 무관한 다수가 함께 차단됨 |
| 차단(식별코드) | 식별 코드 | **정확** — 개인 단위 |

실무적으로 중요한 결론: **`차단(닉네임)`과 `차단(식별코드)`는 이름만 비슷한 전혀 다른
도구다.** `ㅇㅇ` 같은 공용 닉네임에 닉네임 차단을 걸면 광범위한 오차단이 되고,
개인을 겨냥하려면 반드시 식별코드를 써야 한다. 그리고 검색·메모 계열 메뉴는
이미 uid를 타고 들어가므로, 사용자가 걱정한 "반고닉이라 검색이 섞이는" 문제는
**DC 기본 기능 수준에서 이미 발생하지 않는다.**

## 6. 현재 확장 코드의 상태

### 6.1 이미 개인 단위로 동작하는 부분

작성자 정규화 키가 uid를 최우선으로 쓴다.

```js
// src/core/archive/archive-db.js:112
static authorKeyOf(item = {}) {
  if (item.authorId) return `uid:${item.authorId}`;
  if (item.ip)       return `ip:${item.ip}`;
  return `nick:${item.author || ''}`;
}
```

`src/features/user-analytics-feature.js:71`도 같은 우선순위를 쓴다. 반고닉은 `authorId`가
채워지므로 `uid:guest1433` / `uid:chartman` / `uid:table9132`로 **자동으로 갈라진다.**
아카이브 인덱스도 `['galleryId', 'authorKey']`(`archive-db.js:55`)라서, 활동 조회·지분율
집계가 반고닉 개인별로 이미 정확하다. 즉 **이 부분은 고칠 것이 없다.**

### 6.2 표기 문제 (동작에는 영향 없음)

여러 곳이 "uid = 고닉"이라는 이분법으로 서술돼 있어, 반고닉이 고닉으로 오분류된다.

- `src/core/filters/user-rule-manager.js:8-12` — 신분 설명 docstring
- `src/core/archive/archive-db.js:108` — "고닉은 uid, 유동은 IP"
- `FEATURES.md:47`, `README.md:27` — "고닉(uid)/유동/IP 대역"

`matchUserRule()`의 실제 매칭 로직은 uid를 문자열로 비교하므로 **동작은 정상**이다.
순수하게 용어·문서 층위의 문제다.

### 6.3 실제 결함: `userNotes`의 키가 자유 입력

`UserNotesFeature.setNote(userKey, ...)`는 임의 문자열을 키로 받는데, 유일한 호출부가
설정 페이지의 **수동 입력창**이다.

```js
// src/ui/options/options.js:345-352
const key = document.getElementById('un-key').value.trim();
...
await userNotesFeature.setNote(key, note);
```

사용자가 `ㅇㅇ`이라고 입력하면 그 메모는 위 표의 10명 전체를 가리키는 셈이 되어
의미를 잃는다. 작성자 요소에서 키를 받아오는 경로가 없어서, **정작 이 기능만
사람 단위로 동작하지 않는다.**

주의할 점은 확장에 메모가 **두 갈래**로 존재한다는 것이다.

1. `userNotes` (위, 설정 화면 전용, 구분력 없음)
2. `UserRuleManager`의 `action: 'label'` — 활동 팝오버의 "메모 추가" 버튼
   (`user-analytics-feature.js:131-146`)이 쓰는 경로. 이쪽은 `authorKey`에서
   `uid`/`ip`/`nick` 타입을 뽑아 넘기므로 **반고닉에 대해 정확하다.**

따라서 "지금 당장 사람별 메모를 제대로 쓰는 방법"은 설정 화면이 아니라,
목록/댓글에서 작성자를 **Alt+클릭**해 뜨는 활동 팝오버의 "메모 추가"다
(Alt 조건은 `user-analytics-feature.js:49`에서 DC 자체 메뉴와 충돌을 피하려 걸어둔 것).

## 7. 개선 제안 (이번 범위 아님 — 구현하지 않음)

우선순위 순으로, 근거가 확보된 것만 적는다.

1. **`userNotes`를 정규화 키로 이관** — 작성자 요소에서 `authorKeyOf()`와 같은 규칙으로
   키를 만들어 넘기고, 설정 화면의 자유 입력은 마이그레이션 대상으로 둔다.
   (§6.3의 유일한 실제 결함)
2. **신분 분류 함수 도입** — `data-uid`/`data-ip`에 `writer_nikcon img`의 파일명
   (`fix_nik` vs `nik`)을 더해 `고닉 | 반고닉 | 유동닉`을 반환하는 순수 함수. 픽스처에
   50건의 정답 데이터가 이미 있어 그대로 테스트로 쓸 수 있다.
3. **UI에 신분 표기** — 팝오버·라벨에 신분과 uid를 함께 보여, `ㅇㅇ` 3명이 눈으로도
   갈라지게 한다. (사용자가 겪은 "굳이 체크해야만 구분"의 직접적 해소)
4. **닉네임 규칙에 경고** — `nick` 타입 규칙 추가 시 해당 갤러리에서 그 닉네임을 쓰는
   서로 다른 식별자 수를 세어 보여준다. `ㅇㅇ`이면 "10명에게 적용됨"이 뜨는 식.
5. **문서·주석의 이분법 수정** — §6.2 목록.

## 8. 신뢰도와 한계

- **강한 근거(실측)**: 세 신분의 DOM 신호와 `fix_nik`/`nik` 상관, 2옥텟 IP,
  `ㅇㅇ` 10명 사례, 그리고 §6의 코드 인용 — 모두 저장소 파일에서 직접 확인했다.
- **단일 표본 주의**: 아이콘 상관은 픽스처 한 개(한 갤러리, 한 시점, 50건) 기준이다.
  방향은 분명하지만, 분류 함수를 구현한다면 다른 갤러리·모바일 뷰·댓글 영역에서
  재확인이 필요하다. 특히 댓글 영역은 셀렉터가 `.cmt_nickname, .nickname`
  (`src/adapters/selectors.js:116`)이고 아이콘 마크업을 별도로 확인하지 않았다.
- **해석(추정)**: 반고닉이 "회원이면서 닉네임을 고정하지 않은 상태"라는 설명은 DC가
  공식 문서화한 것이 아니라, 관측된 DOM(계정 uid를 가지면서 닉네임이 겹침)에
  들어맞는 해석이다.
- **검토 중 폐기한 가설**: 초기에는 "반고닉 uid가 닉네임+비밀번호에서 파생되므로 서로
  다른 사람의 uid가 충돌할 수 있다"고 가정했으나, 증거가 이를 **반박**했다.
  `guest1433`·`chartman`·`table9132`는 모두 갤로그 주소가 실존하는 계정 ID다.
  이 정정이 문서의 결론을 바꿨다 — 반고닉은 구분 가능하다.
